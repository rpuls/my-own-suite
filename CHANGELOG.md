# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

### Changed

- Defined independently versioned, source-addressed app packages whose installed snapshots retain matching setup and privacy information while newer candidates are discovered separately, plus public workflows for onboarding, breaking-change-aware updates, evidence-backed MOS Privacy Posture assessment, and a phased implementation plan for official and external package sources. The implementation contracts add minimum MOS compatibility, canonical cross-platform package digests with strict file/path limits, fail-closed source trust/privacy/advisory validation, source/catalog/snapshot/advisory/update schemas, a generated drift-checked official app catalog, persisted installed source/snapshot/privacy identity, and narrow root-agent snapshot operations. New installs atomically copy and re-verify approved package files without replacing installed state; confirmed updates are re-downloaded and re-compared against their digest-pair confirmation token, staged into private agent-owned state, and prebuilt before runtime changes. Contract-v5 agents then activate and health-check the exact candidate with existing named volumes, restore the old runtime/routes on activation failure, reconcile cross-app networks, atomically promote the candidate snapshot, retain one previous snapshot only for declared rollback-safe updates, and commit package/privacy/projection identity in one SQLite transaction. Every boundary records a durable operation stage so incomplete integration, promotion, or database work is explicit rather than reported as success. Installed catalog details, guides, icons, integrations, runtime rendering, and Docker builds use the installed snapshot even when the moving repository checkout changes or disappears, while built images/running containers retain exact package-version, digest, and source-revision labels. Existing app rows migrate at startup only when the recorded version and manifest digest exactly match validated source; mismatches become explicit package-recovery state. Whole-suite backups now include exact installed snapshots and source identity, hash every package/state/volume payload, and validate compatibility before destructive restore. Suite Manager resolves the official catalog branch to one immutable Git commit, periodically refreshes an atomic last-known-good cache with bounded requests and backoff, exposes manual Refresh, and shows read-only update or integrity-conflict status without reshaping installed app details. Update preparation downloads candidates into isolated bounded directories, verifies the catalog digest before accepting build inputs, checks MOS/app-agent compatibility, and presents structural, privacy, migration, owner-action, backup, downtime, and rollback differences without mutating the installed app. Compatibility note: installers and reconciliation reserve the root-agent-owned, Suite-Manager-readable `<MOS_V2_STATE_ROOT>/app-packages` snapshot root and the private `<MOS_V2_STATE_ROOT>/suite-manager/app-candidates` update source; the app agent now advertises contract version 5; package-aware bundles use backup schema 2 and reject earlier pre-snapshot bundles; rollback remains bounded rather than guaranteed across data migrations.

    Applied Homepage entries now participate in that update orchestration under their stable instance ID: candidate metadata replaces the existing tile, later failures restore the previous tile, and apps the owner never added remain absent.

    Contract-v6 agents add an explicit digest-bound rollback action for failures after activation and before promotion. Suite Manager classifies interrupted durable stages at startup as retry-safe, rollback-required, or commit-required and exposes that state with the installed app. Core updates no longer show a manual app-reapply warning because installed runtimes and build definitions are bound to their preserved snapshots. Compatibility note: transactional app apply now requires app-agent contract version 6.

    Laid the trust and capability groundwork for non-official package sources: a constrained capability profile that fails closed on privileged containers, host networking, the Docker socket, host path/device mounts, raw proxy config, and host-agent/systemd escape hatches so external packages can only expose declared routes and named volumes; collision-safe namespaced instance identity that keeps official ids bare while isolating other sources by repository and path; an impersonation guard that blocks external packages from reusing official ids, reserved prefixes, or self-asserted review; and a requested-permission surface with increase detection for owner consent before install and before an update widens what a package can reach. Owner-added sources are now recorded in a dedicated store table kept separate from package metadata: sources must be uncredentialed HTTPS (with `local`/`file` sources development-only), bind their immutable revision only after resolution, carry publisher/signature/trust independently of the package's own claims, and follow a gated status model where unreachable or key-rotated sources block new installs recoverably while compromise and removal are terminal — and removing a source only marks matching installs source-orphaned, never uninstalling their preserved snapshots. External candidates are now fetched through the same revision-bound, byte/file-limited download path as the official catalog and must pass the constrained-capability and non-impersonation gate before any build or apply can consume them: malicious path traversal, host-path/Docker-socket mounts, privileged manifests, official-id impersonation, and platform-incompatible packages are rejected while a validated candidate carries its unverified trust, source-namespaced instance id, and requested-permission surface. An owner-only backend source service now orchestrates this over the persisted registry — adding a source resolves its branch to an immutable commit before it is stored, previewing a candidate returns the requested-permission set and trust for consent, and removing a source is metadata-only: it marks the source removed and reports which installs become source-orphaned without ever uninstalling a snapshot or breaking those apps' lifecycle management. These operations are exposed over authenticated owner-only HTTP routes for adding, listing, previewing, status-changing, and removing package sources, with validation failures, non-installable sources, and rejected hostile candidates returning distinct status codes. Third parties publish an app package as a `.mos/` folder at their repository root, so an owner previews one by pasting just the repository URL into the Apps search: a stateless resolve route parses the URL against a git-host allowlist (GitHub first), resolves an immutable commit, downloads a provider-neutral repository archive, extracts only `.mos/` through a hardened tar reader that fails closed on symlinks, path traversal, extended headers, and size overruns, then returns an external, unverified app card — the package's own icon inlined, requested permissions listed, package id read from the manifest — importing nothing until the owner installs.

- Added a plain-language privacy score to app presentation: Suite Manager's app detail replaces the Setup facts tile with a Privacy tile showing a shield stamp (0-10 score derived from the five assessment dimensions) and the installed package's posture, opening a dialog that breaks the score into per-dimension verdicts with review provenance and a link to the assessment docs, always rendered from the installed snapshot's privacy review rather than the moving repo candidate. Update previews show the installed-versus-candidate privacy change as a dedicated before/after row, and public site app pages show the same tile and dialog for the current package. Apps without a completed MOS review truthfully show "Review required / not yet rated". Suite Manager and the public site intentionally carry sibling copies of the shared posture model and components (marked in-source) until a shared UI library exists, and repo-path installs of packages that ship a privacy review now adopt the review's declared source revision so reviewed packages remain installable. An official advisory feed (`apps/advisories.json`) is now fetched from the same immutable catalog revision and shown against the exact package version an owner runs: the Privacy tile flags active advisories and the posture dialog lists each advisory's type, severity, summary, remediation, and evidence link, kept separate from the installed assessment so a corrected or invalidating advisory changes what owners see without rewriting the stored review, while the dialog and public app pages also show the review's provenance (AI-assisted or human review, human-checked). A malformed or unreachable advisory feed keeps the last-known-good catalog. CI now runs the catalog/advisory drift check, the privacy-binding check, and a new stale-review and advisory-invalidated-version monitor (`npm run apps:privacy:monitor`). with bounded, expiring progressive backoff per client address plus a looser account-wide limit for distributed attempts. Throttled requests return a retry interval, successful login clears relevant backoff, and forwarded client addresses are trusted only across Suite Manager's loopback Caddy boundary. Throttle events are persisted as pseudonymous hourly SQLite aggregates with 30-day retention and a 5,000-row hard cap, providing a bounded foundation for a future owner-facing security monitor.
