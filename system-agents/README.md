# MOS System Agents

Host-side privileged agents live here.

Use this area for service, update, backup, and restore agents. Suite Manager talks to these agents through narrow local APIs instead of gaining broad host privileges.

## What a failure carries

Every agent runs its privileged commands through `lib/command-output.cjs`. The runner keeps a bounded rolling tail of what a command writes and, when the command fails, hands back its last 60 lines (at most 8 000 characters) with the exit code or the deadline that stopped it. A command that overruns its deadline is stopped together with the process group it started, since `npm run` and `docker build` do their work in children. Each agent attaches that to its fixed error sentence as `details`, so a failed `docker build`, a Caddy validation that rejected a file, or a service that would not restart travels with its reason to Suite Manager, into the persisted operation record, onto the screen that reports it, and into the file an owner sends for help.

What is never captured is the command line. App containers are started with materialized secrets on their argv, so an error path that echoed what it tried to run would leak every secret of an app at once. A failure is described under a label the caller chose — `docker build for service "web"`, `systemctl restart mos-homepage.service` — and the arguments stay in the process table where they always were. Output is masked by exact value for whatever the agent itself materialized, such as the environment values on a `docker run` or the Cloudflare token, before it leaves root; Suite Manager masks it again against the full secret set it holds before the text reaches SQLite. Neither mask guesses at what a secret looks like.

## HTTPS Agent

`https/agent.cjs` is the first MOS privileged agent. It runs as root and exposes only status plus Cloudflare DNS-01 apply, commit, and rollback over `/run/mos-https-agent/agent.sock`. The socket is writable only by the dedicated `mos-agent` group.

The agent validates the exact structured request, verifies the pinned Caddy module, verifies the Cloudflare token and readable active zone, and stores the token only in `/etc/mos/secrets/caddy-cloudflare.env` with mode `0600`. It creates a root-only checkpoint, atomically installs the secret and repo-rendered Caddyfile, validates and reloads Caddy, and restores the checkpoint on failure. Its error sentences are fixed per code; a failure's `details` carry the last output of the command that failed, or what Cloudflare answered, with the token masked, and never a command line or a request value. A restore that fails too reports both reasons, the apply's first, and keeps the checkpoint on disk.

Suite Manager persists active non-secret state before committing the short-lived checkpoint. If persistence fails it requests rollback. Suite Manager itself is never restarted during an HTTPS apply.

## Homepage Agent

`homepage/agent.cjs` runs separately over `/run/mos-homepage-agent/agent.sock`. It exposes only status, allowlisted file read/validation/apply, add-link, add-home-service, and stable-ID remove-link operations. It has no arbitrary path, shell, service, command, or Caddy-text capability.

The agent validates strict YAML and MOS proxy metadata, stages `services.yaml` and the separate MOS-owned route snippet, runs Caddy validation, atomically writes, restarts Homepage only when required, and reloads Caddy only for changed routes. Any validation, restart, or reload failure restores the known-good Homepage and route files and reports what `caddy` or `systemctl` wrote; a restart or reload failure adds the last lines of the unit's own journal, read before the rollback restarts the unit so the log still ends with the failure rather than the recovery. It never restarts Suite Manager and never modifies the HTTPS agent's main Caddyfile or DNS token state.

Homepage restarts have a dedicated 60-second deadline rather than the generic 20-second command deadline. Suite Manager's socket client waits longer than that operation, and its systemd unit is not stop-coupled to Homepage, so the request remains connected until the transaction succeeds or returns a controlled failure.

## App Runtime Agent

`apps/agent.cjs` runs over `/run/mos-app-agent/agent.sock`. It accepts bounded structured projections and host-owned package snapshot identities, never repository-relative build paths. Its narrow capabilities create and verify official or external snapshots, apply/stop/remove multi-service runtimes, check health, connect declared package networks, and stage, build, activate, roll back, promote, recover, and reclaim transactional app updates. It builds only package-owned Dockerfiles from a digest-verified installed or candidate snapshot, creates package-owned networks, publishes only structured public routes on assigned loopback ports, writes package-scoped Caddy blocks, reloads Caddy, and waits for loopback health. It reports its host architecture so Suite Manager can reject incompatible packages before building.

Every container it creates is given `--log-opt max-size=10m --log-opt max-file=3`. Docker's json-file driver is otherwise unbounded, so one app logging on a loop fills the root disk and takes the suite down with it. The caps are per container rather than a daemon-wide `daemon.json` default, because changing that requires restarting dockerd and so stopping every running app; a container created before this applies picks the caps up the next time its app is applied or updated.

`backup/agent.cjs` runs over `/run/mos-backup-agent/agent.sock`. It owns the backups on every place the storage module lists (it opens drives and holds bucket connections; no place has to be chosen for backups first), whole-suite backup jobs, restore point listing, queued delete jobs, and confirmed restore jobs. Under `MOS-backups/` a drive or a bucket holds one archive per server, `archive-<8 hex>/`, each an encrypted, deduplicating restic repository with a descriptor naming the server that created it, plus one checksummed manifest per restore point: the manifest records installed source identity, the app-package inventory with per-file hashes, and the snapshot ids holding Suite Manager/Homepage/Caddy/HTTPS state and each app Docker volume. Restore validates those identities and payloads — reading back every snapshot the point names — before stopping services, restores package snapshots before app reconciliation, then starts the control plane again. Deleting a restore point forgets its snapshots and runs repository maintenance, which is why it is a queued job rather than an inline call: maintenance rewrites the shared repository and must never overlap a writer. A backup whose worker was killed leaves data the repository no longer references and runs none of its own cleanup, so the agent records the destination and collects it at the start of the next job for that destination — inside the pipeline for the same reason, and reported rather than raised if it fails, so housekeeping never costs the owner the backup they asked for. A snapshot preserves the build definition but cannot guarantee that a third-party registry still serves every pinned base image; unavailable artifacts fail visibly instead of being replaced.

The agent takes drives from the app agent's inventory (`survey()` in `backup/agent.cjs`) and never writes drive records. A place is every connected drive whose format holds backups and every bucket connection; a backup can go to any of them, a drive only while it is mounted read-write, so a backup never writes into a mountpoint a pulled drive left behind. A place carries the storage module's `state` and `reason` word for word, and the agent adds no wording of its own; when the app agent cannot be reached, the drives this server last backed up to (`last-backups.json`) are still listed, with state `unreachable`, so the schedule skips a run with that reason rather than calling a drive not connected. Every archive in every place is listed, this server's and other servers', with whose key opens it (`own`, `borrowed`, `locked`), which server wrote it, and the place it sits in (`placeId`, `placeKind` of `disk` or `object`, `placeLabel`), as is every restore point. On a drive an archive is listed by its folder name plus either a readable descriptor or a repository, and `descriptor: null` is a stated fact: the descriptor is written atomically, a repository without one is probed like any other, and health answers `empty` only when no repository exists, so a torn descriptor never makes a backup start a second archive beside a full one. A bucket has no folders to list, so it keeps a catalog beside its archives, `MOS-backups/catalog`: a restic repository with a published password (`mos-backup-catalog`) that says what a drive's plaintext descriptors say, one tagged snapshot per archive naming the server that made it, written before the archive's repository. The archive MOS 0.22 kept at a bucket's `MOS-backups/repository` is read where it lies, as the archive named `repository`. A backup goes to this server's archive in the place, created beside the others by the first backup there; a repository the key does not open is `locked` and is never written into. Unlock, keys, forget-key and erase take an archive id (`<fsUuid>/archive-<hex>` or `object:<id>/archive-<hex>`) at `/v1/archives/*`. Restoring another server's archive adopts its key, and with no default backup destination set makes that archive's place the default. Above `backup/destinations.cjs` nothing distinguishes a drive from a bucket: both answer whether they are reachable, how much room is left, open a repository, and list, read, write or remove a restore point. MOS implements no part of the S3 protocol — every request is restic's, with credentials passed in its environment rather than its argv, read from the storage record, which is root-only and never backed up. Because there is no filesystem beside a bucket's repository, a restore point stored there keeps its manifest and its operator note as tagged snapshots *inside* the repository, authenticated by the repository's own encryption instead of a checksum file; a drive keeps the sidecar files it always had. Listing a bucket costs network requests, so the agent holds a local index of each bucket archive and of each bucket's catalog, rebuilt from the bucket whenever missing or stale — manifests are immutable once written, which is what makes it safe to trust between refreshes, and it is a cache rather than an authority. A bucket has no free-space figure to refuse a backup against and no unmount to guard against, so those two checks apply to drives only. Where scheduled backups and the one before an update go is one choice, the default backup destination (`primary-destination.json`), set from the schedule or with a backup taken by hand.

The agent also holds the clock for automatic backups. A schedule is one root-owned file in the agent state directory — frequency, wall-clock time, an IANA zone, a destination and a keep-last count — and a timer inside the agent decides when it is due, then hands the work to the same job pipeline an owner's click uses. Due-ness compares the most recent occurrence against the last run rather than counting elapsed time, so a machine that was off through its window backs up once when it returns instead of not at all or once per missed day; a destination that is not mounted holds the run open rather than failing it, and a destination is named by its drive's filesystem UUID, so a changed mount path does not lose it. Retention prunes only restore points whose manifest records `initiator: schedule`, oldest first and only after a new backup has succeeded, through the ordinary queued delete job.

The repository password is generated on the machine, kept root-only in the agent state directory, and never backed up — a backup that carried its own key would not be encrypted in any useful sense. Restoring onto the same machine therefore needs nothing extra; restoring onto a replacement machine needs the recovery key the owner saved, entered on that machine before the destination can be read.

Suite Manager owns app install intent and SQLite projection state. The app agent owns privileged Docker, Caddy route writes, health probing, snapshots beneath `MOS_APP_PACKAGE_ROOT`, and candidates beneath the private `MOS_APP_CANDIDATE_ROOT`. Official snapshot creation derives its source from `MOS_APPS_ROOT`; external snapshot creation resolves the supplied candidate and root through canonical filesystem paths before reading it. Both validate package identity and digest and atomically promote files without replacing installed state. Runtime apply re-verifies the installed snapshot before building. Update promotion keeps at most one previous snapshot only when rollback is declared safe; that copy supports bounded transaction recovery and forensics, not an owner-facing data rollback guarantee. Reclamation removes only digest-qualified package images unused by containers. Stop preserves routes, Homepage entries, volumes, config, secrets, and snapshots. Remove deletes only the named package runtime, routes, MOS-named volumes, images, and instance snapshot. The agent never accepts arbitrary Docker commands, raw Compose/Caddy, host paths, or broad host lifecycle requests; the one host folder a service can reach is a storage folder, which the agent builds itself from a drive id and a folder name (below).

### The storage module: drives, buckets and what claims them

`lib/storage-registry.cjs` is the storage module's record, `storage.json` in the state root (root-only, under the lock file `storage.json.lock`, machine-local and never in a backup): per drive, keyed by filesystem UUID, the owner's name for it, the apps that keep folders on it, whether it is kept open for its files, and its eject and problem state; per bucket, keyed by its `object:` id, the connection the owner typed in, keys included. Ownership is per field: the app agent and its attach unit write drive records, the backup agent writes bucket records, since it holds their keys, and the owner's name for any entry, drive or bucket, is written by the storage module's rename alone; every write takes the lock. Suite Manager merges the app agent's `GET /v1/storage/inventory` (every drive plugged in or remembered, the system drive, the buckets without their secrets, and a detected install stick) with the backup agent's status into the one list its screens read (`GET /storage`), with each entry's capabilities (`holdsAppFolders`, `holdsBackups`, `ejectable`, `checkable`, `renamable`), whether the backup agent answered (`backupsKnown`) and the display name of each app that keeps files on a drive (`appNames`).

### App folders on storage drives

A package that declares `storage` folders gets them as read-only binds from a drive the owner picked, and nothing else from the host. `apps/storage.cjs` owns those drives: it lists filesystems off the system disk; exFAT, NTFS and FAT32 can hold app folders, because they carry no Unix permissions and the mount options `uid=0,gid=0,fmask=0133,dmask=0022` make every file readable by any container user, and ext4 can hold only backups (mounted `noatime,nodev,nosuid,noexec`). It mounts a drive by filesystem UUID at `/media/mos-storage/<uuid>`, creates `MOS-files/apps/<package>/<folder>` on it only after `findmnt` proves the drive is the mount, and records which packages use which drive in the storage record. Each bind is a `--mount type=bind,...,readonly`, which refuses a missing source instead of creating it, so an app whose drive is away fails to start rather than reading an empty folder on the system disk; the apply prepares folders before stopping the running app, so a missing drive leaves it running. Containers carry a `mos.storage-drive.<uuid>` label.

The udev rule `/etc/udev/rules.d/90-mos-storage.rules` starts `mos-storage-attach@<uuid>.service` for every exFAT, NTFS, FAT32 or ext4 filesystem that appears, at boot or when plugged in. `apps/storage-attach.cjs` mounts every drive the rule announces, replacing any stale mount a pulled drive left, so Storage says what a drive holds before anything claims it; only for a remembered drive, one an app reads or one kept open, does it also restart the labelled containers so their binds point at the fresh mount. Uninstall releases the package's claim and never touches the folders; the drive stays remembered, so it is mounted after a restart and its folders stay listed. `GET /v1/storage/usage` lists every `MOS-files/apps/*/*` folder on the mounted drives with its size, including those of uninstalled packages, and what `MOS-backups` takes on each. `POST /v1/storage/rename` sets the owner's name for any drive or bucket without touching the drive's own label, `POST /v1/storage/use` opens an ejected drive again without replugging it, `POST /v1/storage/open` opens a drive nothing keeps anything on yet and keeps it open (`keepOpen`), so its files can be browsed, and `POST /v1/storage/forget` forgets an unplugged drive no app reads. A drive is remembered, and listed while it is away, while an app reads it or it is kept open; backups claim no drive, since every drive is opened on sight. Releasing an app's last claim keeps the drive open rather than forgetting it, and forgetting is only ever the owner's explicit action.

A USB or removable disk whose EFI partition carries the image's own `mos-image.json`, whatever on it is already mounted, is reported as the MOS install stick and never as a drive; `POST /v1/storage/format-installer` erases only a disk that is proven to be the stick at that moment, into one exFAT partition labelled `MOS STORAGE`.

An NTFS drive ntfs3 refuses read-write, because it was unplugged or lost power while mounted, is mounted read-only instead and its apps restarted on it; ntfs3's `force` option is never used. The kernel line that explains the refusal is kept in the storage record with the drive's state. Each drive reports its `state`: `ready`, `read-only`, `failed` (connected but not mounted, with `reason` and the command's or kernel's `detail`), `away`, `ejected`, or `available` for a drive nothing is kept on. `POST /v1/storage/check` stops the drive's labelled containers, unmounts every mount of the drive, runs `ntfsfix --clear-dirty`, mounts it again and starts the containers whatever the outcome; `POST /v1/storage/eject` stops them and unmounts every mount without `--lazy`, refusing with the reason if one stays busy. All three drive actions, and formatting the install stick, are long enough to be Suite Manager jobs.

Secret material is resolved before the request crosses into the app agent. Suite Manager stores raw generated package secrets only in its restricted app secret directory and sends materialized environment values to the agent for the single apply request. If a secret reference is missing, unreadable, or outside that directory, runtime apply fails with `APP_SECRET_UNAVAILABLE` before the agent is called. A build or `docker run` that fails reports the command's last output with the service's secret-shaped environment values masked; a health timeout, where nothing exited non-zero, reports each container's state and last log lines instead.

## Vault Agent

`vault/` owns the encrypted partition that holds everything of the owner's, and it is two units rather than one. `vault/open.cjs` runs as `mos-vault.service`, a oneshot gate that lays the disk out on a machine's first boot and opens the vault on every boot after it; `vault/agent.cjs` runs as `mos-vault-agent.service` and is the one MOS process that keeps running while the vault is locked.

The gate exits 0 when the vault is open **and** on a machine that has no vault at all — a cloud install, or a disk too small to hold one — because those machines are meant to run. It exits non-zero only when a vault exists and did not open. Every unit holding owner data carries `Requires=mos-vault.service`, including drop-ins on Docker's own `containerd.service`, `docker.service` and `docker.socket`, so a locked machine has no dockerd, no Suite Manager and no agent, and nothing can start against the empty directories the vault mounts over. Ordering is `Before=basic.target`, because on a first boot this is what claims the rest of the disk.

The vault is not in `/etc/crypttab` and its swapfile is not in `/etc/fstab`. Both would make a locked disk a failed boot, and a headless machine that fails to boot cannot ask its owner for anything. What the gate cannot do is wait: it fails fast, and the agent serves the page instead.

`vault/layout.cjs` is the disk arithmetic — the system cap, the alignment, the refusal to shrink or to touch a partition MOS did not create — and it is pure so that the one irreversible operation in the product is unit-tested. `vault/agent-core.cjs` is the state machine over an injected adapter, `vault/system-adapter.cjs` the privileged commands, `vault/page.cjs` the locked page. Every sentence the agent can put in front of an owner is in `SENTENCES` in the core rather than at its call sites.

Creating a vault is refused unless `/etc/mos/vault-armed` exists. The published image is baked by running the installer inside a VM and snapshotting the disk, so a vault created during a bake would be written to every download with one key shared by all of them; `mos-image-finalize` writes that file as its last act and fails the build if it finds vault state or a LUKS partition on the bake.

The recovery key is one key with two users, and `lib/recovery-key-store.cjs` owns its files: the key file inside the vault at `/var/lib/mos/backup-agent/engine-key`, the record beside it that says whether the owner has confirmed they hold the key, and the escrow on the plaintext partition that exists only until they do. The gate and the backup agent both call the store and neither knows the other's paths. The gate writes the key at creation, before the backup agent has ever started, so the owner has one secret rather than two. Reading the disk key out of the vault it opens is not circular: the owner's paper copy and the TPM are what open it, and the file is only ever needed once it is already open.

A wrong key is answered as a wrong key and a mistyped one as a typo, by the same checksum the backup agent uses. Attempts are serialised — two `cryptsetup` processes must never open one device at once — with a one-second floor charged per source rather than per machine, so somebody hammering the form from outside cannot make the owner wait for every one of their own tries. The floor is not against guessing, which 140 bits settles; it is because each attempt costs an Argon2 hash and the form is reachable by anyone who can reach the server.

How the chip is enrolled is a property of the machine, recorded in the descriptor as `tpm.mode` (`automatic` or `password`) and `tpm.slot` (`enrolled` or `needs-repair`), and both are read through `vaultAsksForPassword`/`vaultChipNeedsRepair` in `shared/vault-contract.cjs` so nothing re-derives them. `automatic` is the default and seals to PCR 7 alone; `password` adds `--tpm2-with-pin=yes` with the owner's Suite Manager password as the PIN. PCR 7 is deliberate in both: the system partition is plaintext and unmeasured, so an attacker with the machine in hand edits it offline and boots it back with every PCR unchanged, and measuring more of the boot chain would protect nothing that cannot be edited. In `password` mode the gate does not attempt the chip at all — it holds no password — and exits into the page with `needs-password`.

The chip's secret is an opaque PIN everywhere in this agent: `enrollTpm()`, `luksOpenWithTpm()`, the descriptor and `POST /v1/vault/tpm` never learn that it is the owner password, so another source for it later is a caller rather than a redesign. Enrollment is authorised by this machine's own recovery key, read from the vault it is already inside, and wipes any existing chip slot in the same invocation. Every failure path wipes the chip slot and records `needs-repair` rather than leaving one that may still hold a replaced password; the recovery-key keyslot is never removed except by a deliberate rotation, so the worst outcome anywhere here is an owner typing their key once. After an unlock that used the recovery key the chip is re-sealed against the current measurements — authorised by the key, which someone who has it already has everything of — immediately in `automatic` mode, and as a repair at the next sign-in in `password` mode, where this process has no password to enroll with.

Secrets reach the commands as files, never as arguments and, where a form exists for it, not as environment variables: the recovery key via `--unlock-key-file`, the PIN as both `$PIN` and a `cryptsetup.tpm2-pin` credential file (which of the two a systemd release honours has changed), both under `/run`.

The backup agent owns the other half of the same key. `backup/key-rotation.cjs` replaces it: the vault's disk rekey first, so a vault that will not follow stops everything before anything moves, then the key file through the store, then every destination MOS can reach. A destination that was not attached keeps the previous key, which the engine treats like any other superseded key — `engine-key.superseded` beside the key file — and re-keys on the first probe that finds one, whether that is a minute later or six months. `backup/last-backups.cjs` remembers when each destination last received a backup, so a drive that is not plugged in can still be described: it is the only copy an attacker on this machine cannot reach. Which drives exist is the storage module's.

`backup/carry-over.cjs` is the one compatibility bridge before alpha, dated for deletion at 1.0 (decisions, 2026-10-22): at start it folds a 0.22 `object-destinations.json` into the storage record and rewrites `primary-destination.json` if it named a drive by anything but its filesystem id; on every survey it moves a root `MOS-backups/repository` into an `archive-<8 hex>/` folder on a writable drive and claims a drive still listed in `known-drives.json` through the storage module. Nothing else in the agents knows the old shapes.

## Update Agent

`update/agent.cjs` runs over `/run/mos-update-agent/agent.sock`. It exposes only status, start-job, read-job, and track-configuration operations for managed MOS updates. It does not accept arbitrary shell commands, paths, service names, Docker operations, or Caddy text.

The first apply path is branch-track reconciliation for MOS lab installs. The agent starts each update worker as a transient systemd unit when systemd is available, so the job can survive `mos-update-agent` being restarted by reconciliation. If an older job is left marked running after its worker disappears, the agent marks it failed with a truthful recovery message instead of blocking future updates forever. The worker fetches and fast-forwards the configured branch, installs root workspace dependencies and build tooling from `package-lock.json`, rebuilds the Suite Manager frontend, runs `scripts/reconcile-system.cjs`, and records bounded progress logs for Suite Manager. The reconciliation script refreshes repo-owned host services and agents, including the updater itself, before the job reports success. A step that fails names itself and keeps the tail of what it wrote in the job record, which Suite Manager shows on the Updates screen and includes in the diagnostics bundle; the worker's full stream still goes to the transient unit's journal. Each step has a one-hour deadline, so a stuck step fails the job instead of holding it open forever.

Installed app runtimes are decoupled from the moving repository checkout. Core managed updates refresh every repo-owned host agent, while each installed app continues to run and be managed from its preserved snapshot. Package updates are discovered and applied independently through the app update transaction; a core update does not silently rebuild apps from newer repository package files.

## Diagnostics Agent

`diagnostics/agent.cjs` runs over `/run/mos-diagnostics-agent/agent.sock`. It exposes only status and a single `collect` operation, and that operation **takes no request body at all**: the collector list is compiled into `diagnostics/agent-core.cjs`, so a caller cannot name a unit, container, path, or line count. This is the security argument for the agent, not a convenience — a root process that reads host state on behalf of an unprivileged web app must not be steerable by it, or it is an arbitrary-file-read primitive. Adding a source means editing the list and shipping it. A unit test asserts `collect` has no parameters, so widening it cannot pass unnoticed.

It reads systemd unit states and journals for MOS-owned units, `docker ps` and per-container logs for containers named `mos-*`, and fixed host facts (`uname`, `uptime`, `df`, `free`, `docker system df`). Here command output is the whole result rather than the explanation of a failure, and it is captured on success as well; like every agent it never captures command arguments, for the reason given above.

Collection is best-effort per source. This runs on a machine that is by definition not well, so a collector that fails is an expected outcome, not an exceptional one; each failure is named in `incomplete` and the rest of the bundle is still returned. A collection already in flight is joined rather than duplicated.

The agent performs no redaction. It returns raw text to Suite Manager, which holds the plaintext of every app secret and is therefore the only component that can mask by exact value. Nothing the agent returns reaches disk or a log line before that redaction runs.

## Lab Reset Agent

`lab-reset/agent.cjs` runs over `/run/mos-lab-reset-agent/agent.sock` only on USB/Hyper-V lab installs where `MOS_LAB_RESET_ENABLED=1`. Suite Manager exposes `/suite-manager/api/lab/reset` only when that flag is set; non-lab installs return `LAB_RESET_DISABLED`.

The agent schedules a repo-owned reset worker and returns before Suite Manager is restarted. The worker clears only disposable lab state: Suite Manager SQLite/session/app state, Homepage runtime config, MOS-owned Homepage/app Caddy route snippets, and `mos-app-*` Docker containers, networks, and volumes. It preserves the VM, installed repo checkout, npm dependencies, pinned control-plane images, HTTPS secret files, and backup disk state.
