MOS backs up the whole suite, by hand or on a schedule, to a drive plugged into the server or to storage online: an S3-compatible bucket at a provider of your choice. The practical destination depends on where that server lives.

If you are deciding how many copies to keep and where, read [Keeping copies](/docs/guides/keeping-copies/) first. This page is the mechanics.

:::danger[A backup holds every secret your server has]
Any backup contains your data, credentials, and secrets. It is encrypted with your **recovery key** before it is written anywhere, so a stolen drive or a breached account at your storage provider cannot be read. The server keeps a copy of that key so backups can run without you, which it holds inside its own encrypted vault: on own hardware, a stolen server with password-protected startup on gives up neither the server nor the backups, and with it off a thief who gets past the server has the key to both. You keep a copy too, because it is the only thing that can open these backups on a replacement server.
:::

## Your recovery key

MOS shows you the key once, before your first backup, and will not take that backup until you say you have kept it. It looks like `MOS-7K2F-9XQ4-…`: eight groups of four characters, in an alphabet with no letters that can be mistaken for digits, so it survives being written on paper.

- **Save it somewhere that is not this server.** A password manager, or paper somewhere that is not the building the server is in. Without it, a replacement server cannot read a single backup, and nobody can recover it for you.
- **Download the recovery kit.** A text file with the key, the drives and storage online you have connected, and the steps to recover onto another server. It never contains your storage provider's access key — that lives in your provider's console, and a new key for the same storage works just as well.
- **You can see it again.** **Show key** on the Backup & Restore screen asks for your owner password and then shows the key and offers the kit again, so a kit that has gone stale since you connected new storage can be re-downloaded. It also lists, by name, every place this key opens and every place that still needs another server's key.
- **What the copy on the server does and does not protect.** A key held on the server protects against a stolen drive or a breached account at your storage provider, not against a compromised server: something running on your server with the key can read and delete your backups, which is why [one copy you unplug](/docs/guides/keeping-copies/) matters. It is there so unattended scheduled backups can run.
- **You can change it.** **Show key → Change recovery key** makes a new one and moves this server's disk and every backup it can reach over to it; a drive that was not plugged in catches up the next time you connect it. Changing the key does not make earlier restore points unreadable to someone who already had the old key and a copy of your storage, and the screen says so — if you think that happened, start a fresh archive.

## What a backup contains

A MOS backup captures:

- every installed app and its declared data volumes,
- the exact installed app-package snapshots and settings,
- the owner account, app secrets, and app connections,
- the Home dashboard layout,
- domain and HTTPS configuration.

Files an app reads from a drive you plugged in, such as Jellyfin's films, are not in it: they stay on the drive, which goes with you to any server. See [Your files on a drive](/docs/guides/files-on-a-drive/).

Restore requires a working MOS installation. A backup is not a bare-metal installer by itself. The version does not have to match: MOS restores a backup written by its own release or any earlier one, so a current install reads a backup taken months ago.

## Choose a destination for your installation

### Own hardware

Connect a writable USB disk or other external drive directly to the server. MOS lists every drive you plug in under **Settings → Storage** and opens it on sight, so Backup & Restore can back up to it and see what it holds. A drive formatted as exFAT, NTFS or FAT32 can hold backups and app files; one formatted for Linux (ext4) can hold backups only.

Do not save the only backup on the server's System drive: a disk failure could take out both the suite and its backup.

### Cloud server

A rented server cannot use a USB disk attached to your computer. You have two options: attach a persistent block-storage volume through your provider, format and mount it on the server, and select that mounted volume in Suite Manager; or connect storage online, which needs nothing mounted and can live at a different company from the server. Both are billed separately. A mounted volume stays inside your server provider's trust boundary, so use provider-supported encryption where available; storage online receives only data MOS has already encrypted.

Provider snapshots are outside MOS either way: they may be useful as an additional recovery layer, but MOS cannot verify their consistency, contents, retention, or restore behavior. They do not replace a tested MOS backup.

## Taking a backup

<Steps>

1. Plug in the drive, or connect storage online under **Settings → Storage → Add storage**.

2. Open **Suite Manager → Backup & Restore** and click **Back up now**. The first time, MOS shows your recovery key and asks you to confirm you have saved it before it goes on.

3. Pick the drive or the storage online the backup goes to. The first time, keep **Also make this the default backup destination** ticked: automatic backups go there from then on. Apps pause while their data is captured and start again when the job finishes; the place is then listed under **This server's backups**.

4. Keep the drive itself on access-controlled storage. There is no separate file to download—this server's archive on the drive is the copy you keep, and moving a backup to another server means taking the drive there.

</Steps>

Backups are written under `MOS-backups/` on the drive or in the bucket, into this server's **archive**: one encrypted store per server, shared by every restore point that server writes there. A drive or a bucket can hold the archives of several servers side by side, and this server only ever backs up into its own. An archive is a [restic](https://restic.net/) repository. MOS has no backup format of its own: restic — an open-source backup program in wide use since 2014 — does the encryption, the chunking, the deduplication and the integrity checking, and MOS drives it rather than replacing it. Because the archive is content-addressed, a second backup only writes what actually changed, and one drive holds many restore points for far less space than one full copy each. Each restore point records which stored data it needs; MOS checks the archive's integrity and re-verifies every app package before a restore changes running services.

Backup & Restore looks in every drive and every storage online connected to this server, and lists what it finds in two groups: **This server's backups**, and **Backups from another server**. You can unlock another server's archive with that server's recovery key and restore from it, but this server never changes it; on a drive, **Erase these backups** gives back the space it takes and leaves the rest of the drive alone.

## Backing up somewhere else

A drive in the same room as the server survives a failed disk. It does not survive a fire, a flood, or someone walking off with both. **Settings → Storage → Add storage → Connect storage online** connects MOS to storage at a provider — anything S3-compatible, such as Backblaze B2, Wasabi, Cloudflare R2, Tigris, or a MinIO server of your own — and from then on you can back up to it like a drive.

You need four things from your provider: the endpoint address, a bucket that already exists, and an access key with its secret. A folder is optional; several servers can share one bucket and folder, each with an archive of its own beside a small catalog that says which server made which. **Test connection** tells you whether MOS can reach it *before* it connects, and says which of a wrong key, a missing bucket or an unreachable address it ran into.

- **Your backups are encrypted before they leave the server.** The provider stores what it cannot read. restic encrypts every chunk and its metadata with your recovery key, so nothing MOS uploads is readable without it.
- **Storage online behaves like a drive from there on.** Back up to it by hand or on a schedule, verify a restore point in it, note it, restore from it, delete from it.
- **Nothing is deleted when you disconnect.** MOS forgets how to reach it; the backups in it stay, and reconnecting with the same details lists them again.

:::caution[Storage online is only as recoverable as your recovery key]
The provider holds data it cannot read. Your recovery key is what opens it, and the copy that matters is the one you keep — see [Recover onto a new server](#recover-onto-a-new-server).
:::

## Backing up automatically

The most recent backup you have should not be the one you last remembered to take. Under **Automatic backups** on the Backup & Restore screen choose **Change**, turn the schedule on, pick daily or weekly and a time, and pick the **default backup destination**. That is also where MOS backs up before it updates itself; **Back up now** starts on it too, and you can pick another place for that one backup, so a drive you keep in a fire safe is still one click.

- **Times are yours, not the server's.** The time you pick is read in the time zone of the browser you set the schedule from, so 3am means 3am where you are even when the server runs in UTC. The screen names the zone it is using.
- **A default destination that is not there is not a failure.** If the drive is not connected, or your storage online cannot be reached when the time comes, MOS says automatic backups are waiting and backs up as soon as it can reach it again, up until the next scheduled time.
- **A server that was switched off catches up.** It takes one backup shortly after starting again, not one for every window it missed.
- **Retention prunes automatic backups only.** Keeping the last 7 means the eighth automatic backup removes the oldest, once the new one has succeeded. Backups you took yourself are never removed by retention, whatever it is set to—so a copy you took before a risky change stays until you delete it. The backup MOS takes before it updates itself counts towards the same number, like a scheduled one.

Apps pause for a few minutes while a backup runs, which is worth remembering when picking the time.

:::tip[A workable routine]
Leave a daily schedule on. MOS backs up on its own before it updates itself, so the moment left to cover by hand is a change you are about to make—uninstalling an app, or updating one that migrates data. Periodically check that the destination is still readable with **Verify** on a restore point.
:::

## Restoring

Restore replaces the current suite with a backup on a server that already has a compatible MOS installation.

1. Plug in the drive, or connect the storage online, that holds the backup, open **Suite Manager → Backup & Restore**, and pick the restore point.
2. Type `RESTORE` to confirm.
3. MOS verifies the stored data and each saved app-package snapshot before stopping services. It creates a small rescue copy of current state, restores settings, package definitions, and data, then rebuilds the app runtimes.

Important boundaries:

- **Restore goes forward, never backward.** Each backup records the MOS version that wrote it, and restores onto that version or any later one. Install the current release; MOS does not need, and cannot install, an older version of itself. The one direction that fails is restoring a newer backup onto an older MOS, which MOS reports and refuses rather than half-applying.
- **Restore is whole-suite.** Per-app restore is not supported.
- **The server must already run MOS.** Install MOS first, then plug in the drive or connect the storage online that holds the backup, and restore.
- **A replacement server needs the recovery key as well as the storage.** See below; restoring onto the server that made the backup never asks for it, because that server already holds it.
- **Package snapshots are preserved, registry artifacts are not.** If an upstream registry removes a required digest-pinned image, MOS restores state and reports the affected app as failed rather than substituting another version.

## Recover onto a new server

This is what the recovery key is for: the server is gone — fire, theft, a dead disk — and a drive or your storage online is all that is left. A cold standby kept powered off elsewhere, or any freshly installed server, becomes the one you lost.

<Steps>

1. Install MOS on the replacement server — the current release, whatever the backup was written by — and create an owner account on it so you can sign in. It can be a throwaway account; the restore replaces it with the one from the backup.

2. Plug in the drive. For storage online, connect it in **Settings → Storage → Add storage** with the same endpoint, bucket and folder. Your provider's console holds your access key, and a new key for the same storage works too.

3. Open **Suite Manager → Backup & Restore**. The backups appear under **Backups from another server**, apart from this server's own. Choose **Enter recovery key** and type the key from your kit. Capitals, spaces and dashes do not matter, and a slip is reported as a typo rather than as a wrong key.

4. The restore points appear, each showing which server wrote it. Pick one and restore it as usual.

5. When the restore finishes you are signed out. Sign in with the **owner password of the server the backup came from** — accounts and passwords now match the backup.

6. Plug in the drive that held your app files, if an app used one. The restored apps find their folders on it and carry on; [Your files on a drive](/docs/guides/files-on-a-drive/) explains what lives where.

</Steps>

### If the old server used a domain

Your suite comes back on **this server's own address** — the one you were using while you restored. A restore never changes that, whichever address it is: the Easy Door, the name your own network holds, or a domain you set this server up with before restoring. If you had already given this server a domain, that is what your suite comes back on, and nothing about it changes.

The old server's domain is set aside rather than moved, because a name points at one server at a time. **Settings** names it and offers to serve it from this server in one step: MOS kept the domain's credential from the backup, so you enter no token, and MOS reports success only once the certificate has been issued and the name answers here.

Until that name points at this server, anything set up against the old address keeps failing — phone apps, desktop sync clients, browser extensions. Three things fix that:

- **Point the name here.** Change the record at your DNS provider, and any override your own network holds for it, to this server's address. MOS reads that name and tells you what it currently answers, but it never changes DNS for you.
- **Give the new server the old server's network address**, if the old server is off and both are on the same network. That is a change on your router — a DHCP reservation for the new server — and nothing at your DNS provider has to change. It happens outside MOS, so MOS neither does it for you nor sees that you have.
- **Point your devices at the new address** instead, one app at a time.

**Turn the old server off before you point the name here.** Two servers answering for one suite means two copies of your data drifting apart, and no way to merge them afterwards.

What just happened to the backups themselves: nothing. Connecting to an archive another server wrote never changes it — not its contents and not the list of keys that open it. MOS keeps the key you entered on this server and uses it to read that archive, and **Lock again** on the row takes it back off again.

The key becomes this server's own when you restore another server's backup onto it: the server now holds that suite's data, so it uses that suite's key, and from then on one key opens both the disk and the backups. If the original server comes back on, both can back up to the same drive, each into its own archive; each restore point names the server that wrote it.

## Current limitations

Whole-suite restore only · a restore needs an owner account to sign in with first, so recovery is install, create an account, restore · no automatic backup before an **app** update, only before a MOS update · one default backup destination for the schedule, so a drive copy and a copy online are two separate backups.
