# Paperless-ngx MOS Package

## Services

- `paperless`: Paperless-ngx web and consumer service, exposed through the single public `paperless.<base-domain>` app route.
- `broker`: internal Valkey service. Paperless requires a Redis-protocol broker for its task queue; document consumption, scheduled tasks and the automatic matcher do not run without it.
- `mcp`: the MCP server MOS offers assistants for Paperless (see AI Tools below). Built from the same pinned Paperless image (`Dockerfile.mcp`) for its Python, so it adds no image download.

Only `paperless` is routed through Caddy. The broker is package-internal on the package-owned Docker network. `mcp` has no route either; the host publishes it on loopback so Suite Manager can call it.

The package uses Paperless' built-in SQLite database (`PAPERLESS_DBENGINE=sqlite`). PostgreSQL, Tika and Gotenberg are optional upstream and are not part of this package.

## Environment Variables

- `PAPERLESS_REDIS=redis://broker:6379`: broker connection, addressed by service id on the package network.
- `PAPERLESS_DBENGINE=sqlite`: built-in database; no other connection variables apply.
- `PAPERLESS_URL`: composed as `${app.scheme}://${app.host}`, not `${app.publicUrl}`. Paperless appends its hostname to `ALLOWED_HOSTS` and adds the URL verbatim to `CSRF_TRUSTED_ORIGINS` and `CORS_ALLOWED_ORIGINS`, and django-cors-headers rejects an allowed origin that carries a path. `${app.publicUrl}` always ends in `/`, which counts as a path: it fails the Django system check with `corsheaders.E014`, s6 aborts init, and the container restarts forever without ever serving. Any future variable that takes an origin rather than a base URL must be composed the same way.
- `PAPERLESS_ALLOWED_HOSTS=paperless`: the internal service name, so the MOS health probe reaches a real response instead of a Django `DisallowedHost`. Setting it also takes `ALLOWED_HOSTS` off its `*` default; Paperless then appends `localhost` itself, and `PAPERLESS_URL` appends the public hostname, leaving exactly the three names that legitimately reach the service.
- `PAPERLESS_ENABLE_UPDATE_CHECK=false`: MOS owns app updates, so Paperless' own release check is switched off rather than left to the upstream default. It reaches `https://api.github.com/repos/paperless-ngx/paperless-ngx/releases/latest`. The variable is a UI-level control, not a server-side block: it sets `update_checking.backend_setting`, which the web client copies into a user's `update_checking_enabled` preference only when that preference is unset, and `RemoteVersionView` performs the fetch whenever `/api/remote_version/` is called without consulting the setting. A user who turns the toggle back on inside Paperless will therefore still cause the request.
- `PAPERLESS_SECRET_KEY`: generated by MOS and stored as a secret reference. Paperless refuses to start without it.
- `PAPERLESS_ADMIN_USER`, `PAPERLESS_ADMIN_PASSWORD`: collected during install; Paperless creates this superuser on first start, before its web server answers the health check. The password is `forgetAfterStart`: MOS deletes it once that start is healthy, so every later start runs without `PAPERLESS_ADMIN_PASSWORD`, which Paperless then ignores for an existing superuser.
- `PAPERLESS_OCR_LANGUAGE`: collected during install, default `eng`.
- `PAPERLESS_TIME_ZONE`: collected during install, default `Europe/Amsterdam`.
- `MOS_AI_KEY` on `mcp`: the generated `aiKey` secret, which Suite Manager presents to the MCP server. `PAPERLESS_ADMIN_USER` is passed to `mcp` as well, as the account `/sign-in` signs in to. No password is.

## Volumes And Persistence

- `data:/usr/src/paperless/data`: SQLite database, search index and classification model.
- `media:/usr/src/paperless/media`: the documents themselves - originals, archived PDFs and thumbnails.
- `export:/usr/src/paperless/export`: destination for `document_exporter` runs.
- `consume:/usr/src/paperless/consume`: watched folder; files dropped here are imported and removed.
- `redis-data:/data` on `broker`: queue persistence.

`media` and `data` are the volumes that matter for recovery. Disable stops and removes containers while keeping routes, volumes and stored secret references. Uninstall removes containers, routes, MOS-owned Homepage shortcuts, these Docker volumes, stored config and secrets.

## OCR Languages

The upstream image ships Tesseract data for `eng`, `deu`, `fra`, `ita` and `spa`. The package Dockerfile adds `tesseract-ocr-nld` at build time so Dutch works from the pinned image.

`PAPERLESS_OCR_LANGUAGES` (plural) is the upstream mechanism for adding more, but it apt-installs on every container start, needs the network at runtime and is unsupported in rootless containers. Adding a language to this package means adding its Tesseract package to the Dockerfile and extending the `ocrLanguage` field label, not setting that variable.

Setting `PAPERLESS_OCR_LANGUAGE` to a code with no installed data leaves documents failing in the consumer rather than failing the install.

## Health Check

- `http://paperless:8000/accounts/login/`

The allauth login page, which returns 200 without a session. Note that the MOS probe treats any status below 500 as healthy, so a misconfigured `PAPERLESS_ALLOWED_HOSTS` would still pass while returning 400 - the variable above is what makes this probe meaningful.

## Consuming Documents

Documents can be uploaded through the web interface, which is the path this package expects owners to use. The `consume` volume is a MOS-managed Docker volume, so the watched-folder and scanner-drop workflows described upstream need server-side access to that volume; there is no Suite Manager path to write into it.

## Capability Exports

`exports.documentArchive` publishes this package's REST API to other packages as `document-archive` / `paperless-ngx-rest` interface 1, carrying `internalBaseUrl` (`http://paperless:8000`) and no secrets. A consumer that accepts it receives the internal address and joins this package's network, so an upload never leaves the server.

The capability deliberately carries no credential. A MOS integration can only hand over a secret MOS generated itself, and a Paperless API token is minted inside Paperless's own database; a consumer therefore collects its token from the owner, who creates it under **My Profile** in Paperless.

## Upgrades

Paperless runs database migrations on start, so the manifest declares `backupRequired: true` and brief downtime.

Paperless-ngx 3.0 was a major release: it dropped API versions below 9, removed document and thumbnail encryption, replaced the Whoosh search backend with tantivy, and changed the pre/post consume script arguments. This package's first release pinned 3.0.5, so those breaks do not apply to an upgrade path within MOS, but they matter to anyone importing an export from an older Paperless install.

3.1.3, upstream's rebase onto Python 3.14, carries no documented breaking change from 3.0.5. It adds two scheduled tasks to the six that 3.0.5 shipped: `documents.tasks.llmindex_index` daily at 02:10, which returns immediately unless the owner has enabled AI, and `documents.tasks.cleanup_expired_share_link_bundles` daily at 02:00, which is local. It also spreads the default ten-minute mail poll across the interval using an offset derived from `PAPERLESS_SECRET_KEY`, so the schedule is per-install rather than on the exact minute.

Coming from 3.1.3 to 3.3.0, the first start applies five additive migrations (`documents` 0026-0027, `paperless` 0016-0018), then `init-search-index` wipes and rebuilds the whole search index from the database because its schema version moved from 1 to 3; the webserver does not answer until that finishes, at roughly 500 documents a second on two cores. The classifier format moves from 10 to 11, so the old model is deleted and suggestions return after the next hourly training. 3.1.3 still starts on a migrated database and rebuilds its own index, which is why `rollback` stays `safe`. A new `init-compile-bytecode` step adds a few seconds before migrations, and `/admin/` now signs in through the regular login page, so its two-factor prompt applies there too.

Coming from 3.3.0 to 3.3.4, the first start applies no migrations (`documents` still ends at 0027, `paperless` at 0018), but the search index schema moves from 3 to 4 so that only root documents are indexed, and `init-search-index` rebuilds the index again before the webserver answers. A rebuild interrupted by a restart now leaves a `.rebuilding` marker and is retried on the next start. The classifier format stays at 11. Rolling back to 3.3.0 starts on the same database and rebuilds its own index, so `rollback` stays `safe`. The image moves Pillow from 12.3.0 to 13.0.0, aiohttp to 3.14.4 and certifi to 2026.10.19, which drops the distrusted emSign roots.

Coming from 3.3.4 to 3.4.0, the first start applies no migrations and leaves the search index (schema 4) and classifier (format 11) in place, so the webserver answers as soon as Django is up and rolling back to 3.3.4 stays `safe`. ImageMagick is gone from the image: thumbnails are rendered with Poppler's `pdftoppm`, existing thumbnails are kept, and `PAPERLESS_CONVERT_BINARY`, `PAPERLESS_CONVERT_TMPDIR`, `PAPERLESS_CONVERT_MEMORY_LIMIT` and `PAPERLESS_GS_BINARY` are no longer read; this package sets none of them. The image moves django-allauth to 65.20.1, oauthlib to 4.0.0 and djangorestframework to 3.18.3.

Coming from 3.4.0 to 3.4.2, there are still no migrations, and the search and classifier code is unchanged, so 3.4.0 starts on a 3.4.2 database and `rollback` stays `safe`. The consumer, worker and scheduler now skip Django's system checks, but `init-checks` still runs them once before any service starts, so a bad `PAPERLESS_URL` still stops init. Settings now also refuse a `PAPERLESS_URL` with no hostname. The search index and LLM index init steps now wait for `init-tesseract-langs`, which does nothing here because `PAPERLESS_OCR_LANGUAGES` is unset. The image moves Django to 5.2.18, django-guardian to 3.5.2 and filelock to 4.2.6.

The package now pins 3.5.1, and this is the first update since 3.3.0 that cannot be rolled back, so the manifest declares `rollback: unsupported`. 3.5.0 replaces django-treenode with a plain adjacency list: migration `documents.0028` drops the thirteen `tn_*` cache columns from `documents_tag` and keeps `tn_parent`, so every tag keeps its parent. `0029` adds a Manual workflow trigger type and `0030` adds `format` to notes (default `plain`; Markdown notes are new). 3.4.2 then fails `init-migrations` on the migrated database with `no such column: documents_tag.tn_ancestors_pks`, and Suite Manager's automatic rollback of a failed update would hit the same wall, which is why the update requires a backup and going back means restoring it. The search index (schema 4) and classifier (format 11) are untouched, so the webserver answers as soon as the migrations finish. Bulk edits now return a task id and run in the Celery worker, so an API client must poll the task rather than read the result from the response. A new `Clear expired sessions` task runs daily at 03:00 (`PAPERLESS_SESSION_CLEANUP_TASK_CRON`) and is local. `ALLOWED_HOSTS` now defaults to `*` only when neither `PAPERLESS_ALLOWED_HOSTS` nor `PAPERLESS_URL` is set; this package sets both, so the resulting list (`paperless`, `localhost` and the public hostname) is unchanged. The image moves django-allauth to 65.21.1 and drops django-treenode.

## AI Tools (MCP)

Paperless has no MCP server of its own, so the package ships one: [mcp-server.py](./mcp-server.py), a stateless Streamable HTTP server on port 8100 using only the Python standard library. It answers `POST /mcp` only with `Authorization: Bearer <aiKey>`, where `aiKey` is a setup secret MOS generates at install (`auth.kind: package-secret`), so the owner never handles a token. The export declares `auth.signIn: /sign-in`: when the owner first lets an assistant into Paperless, Suite Manager asks for their Paperless password and posts it once to `POST /sign-in` (same key), which exchanges it at `POST /api/token/` for the owner's own API token and returns it. Suite Manager keeps only that token and sends it on every MCP call as `X-MOS-App-Token`; the service holds no credential of its own and reaches only `http://paperless:8000/api`, at API version 10. [ai-tools.json](./ai-tools.json) offers its tools by kind:

- `read`, run at See: `search_documents` (full text with filters, or newest first, 25 at most per page), `get_document` (labels, notes and recognised text, 12,000 characters per call), `list_labels`.
- `add`, run at See and do: `add_note`.
- `change`, run at See and do: `update_document` sets the title, date, correspondent, document type and tags. A label it does not find is created with matching set to None, so it never starts filing other documents by itself.
- No tool deletes, shares, downloads or reprocesses a document.

A Paperless API token outlives password changes, so changing the password inside Paperless does not stop the tools. Regenerating the token in the Paperless profile does: Paperless then answers 401, the tool result carries `_meta: {"myownsuite.org/sign-in": "refused"}`, and Suite Manager drops the token and asks the owner to sign in again. Output is plain text, kept short so a search fits small local models.

## AI Features

MOS wires Paperless' AI suggestions and document chat to the AI service the owner turns on for Paperless under **Settings → AI in your apps**, through `${ai.*}`:

- `PAPERLESS_AI_ENABLED`, `PAPERLESS_AI_LLM_ENDPOINT`, `PAPERLESS_AI_LLM_API_KEY` (only with a key) and `PAPERLESS_AI_LLM_MODEL`: the service's address, key and chat model. `PAPERLESS_AI_LLM_BACKEND=openai-like` is always set and does nothing while AI is off.
- `PAPERLESS_AI_LLM_EMBEDDING_BACKEND=openai-like` and `PAPERLESS_AI_LLM_EMBEDDING_MODEL`: only when the service has a search model. `get_embedding_model` then sends embeddings to `PAPERLESS_AI_LLM_ENDPOINT`, the same service, since no separate embedding endpoint is set. Without a search model the embedding backend is unset, so `AIConfig.llm_index_enabled` is false: the nightly `llmindex_index` task skips, and no Hugging Face model is downloaded.

With the service off, MOS leaves every `${ai.*}` variable out, `PAPERLESS_AI_ENABLED` stays at its `NO` default, and Paperless calls no AI service. Values the owner sets inside Paperless under Settings still win, because `AIConfig` reads `ApplicationConfiguration` before the environment.

`PAPERLESS_AI_LLM_ALLOW_INTERNAL_ENDPOINTS` defaults to `true` in 3.5.1, which a model on the owner's own network needs, so MOS leaves it alone. `paperless/network.py` still pins each AI request to the address it resolved, so DNS rebinding cannot redirect it.
